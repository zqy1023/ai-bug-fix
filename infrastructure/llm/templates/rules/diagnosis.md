## 异常分析与修复依据

先确定失败阶段，再判断该阶段是否违反已确认的契约。异常名称、HTTP 成功或调用未抛错均不是业务结论。以下是核查方向，不是预设改法；仅处理原始证据实际涉及的情形。

### 先决定是否应修改

只有证据支持纯上游、网络或运行环境故障，且未发现必须修复的本地缺陷时，才跳过修复。连接、代理、超时、依赖或配置失败先沿真实调用核对责任；不能只凭这些异常名称或 response 为空就跳过。不得仅为了更换异常名称、日志文案、告警级别或返回标签而修改源码；现有代码将外部错误包装为解析错误，也不能单独成为本轮修复理由。不因“改动很小”“分类更准确”就把上游责任改称 mixed。

已收到能确认含义的错误回执却仍按正常业务数据解码/解析，是需要修复的本地处理缺口，不属于仅改标签。明确的服务不可用状态、服务器错误页面、业务错误字段或拦截结构，应在正常 JSON/XML/轨迹解析前按现有错误协议处理；例如已有状态或完整错误页能够证明服务器不可用时，返回 ServiceError 和简短原因，不继续触发 JSONDecodeError。上游触发不妨碍修复本地错误响应处理。先确认状态来自当前响应的实际错误区域，不能因正常业务字段/模板里出现错误文字就提前返回；无法判明的空体、未知格式或一般解码失败，不得一律当作 ServiceError。

原始请求、日志、配置与实际源码能够共同证明当前授权代码有必须处理的本地缺陷，就允许修改，不要求一定取得响应或堆栈。无响应可能是请求尚未正确发出、参数/身份/配置传递错误、执行分支提前失败，或异常处理破坏了既有错误协议；沿调用确认输入值、代码条件、违反的契约与最小修改依据。已收到明确服务错误正文却被当作轨迹解析，或业务响应在字段提取、类型处理、映射中失败，也按相同标准判断。必须分别指出外部触发因素、本地缺陷以及修改的必要性；仅外部错误文字、外部恢复、格式合法或无异常返回均不构成证明。response 为空不等于上游故障，也不等于不可修复；本地配置使用错误与部署环境缺配置不能混为一谈。责任仍不明确时先定向核对证据；只有确实无法定位才走补充复现，不把所有不确定情况一概判成上游故障。

审查必须先独立判断“本轮是否应该修改”，再判断代码写法。纯外部故障上的异常标签优化应要求撤销；已确认存在本地处理缺陷的补丁不能仅因上游出错而拒绝。跳过说明失败阶段、外部责任依据和未执行本地修改，不宣称问题已修复或上游已恢复。

先分析已有日志、响应与源码，复现不是分析或修复的统一前置条件。日志已有明确错误、字段、堆栈或可定位的失败条件时，直接分析并在证据充分时修复；缺单号、实时请求失败或未执行复现不能单独成为停止理由。只有日志看不出明确原因，且读取相关源码及已有响应后仍无法定位时，才输出 INSUFFICIENT_EVIDENCE，明确已经检查的路径和缺失事实，由平台按原单号及配置补充请求复现。业务语义决策缺口与无法定位错误分别说明，不用复现代替业务依据。未真实执行时如实标注静态推导，后续独立审查及回归另行记录。

| 现象 | 核查依据与处理边界 |
| --- | --- |
| 连接、超时、代理或依赖失败 | 沿请求构造、参数/配置传递及异常链核对实际失败层；已证明的本地缺陷可修，纯外部故障才跳过，不改标签或重试策略。保留框架超时/取消机制。 |
| 登录失效、访问限制或服务拒绝 | 核对明确状态、业务错误字段或页面结构；区分身份、限流、拦截及暂时服务故障。不凭格式或通用关键词猜原因。 |
| 空响应、非预期格式、解码失败 | 先区分根本未发出请求、未收到响应、正文为空及日志未记录响应，再核对对应源码和原始请求；不以缺 response 判不可修复。不自动返回无单或成功。 |
| 缺字段、null、类型或嵌套变化 | 确定字段在当前分支是必需、可选还是业务缺失信号。可选字段容错须有依据；必需字段缺失保留明确错误，不层层补空值。 |
| 无记录、无事件或部分数据 | 区分实体不存在、已有实体暂无事件、查询条件不符及数据不完整。只有明确业务依据才能转换状态。 |
| 时间、状态、地点或事件映射错误 | 核对字段含义、时区、排序、去重和状态优先级。不删事件、统一替换时间或改最终状态来掩盖异常。 |
| 批量、渠道、分页或多种响应分支 | 保持请求单号与结果逐项关联，检查分页完整性、分支条件与回退优先级。不因一个样本统一所有分支格式。 |
| 框架协议、共享层或环境不匹配 | 核对真实入口、返回模型及依赖，分别报告本地与范围外责任。不通过修改共享代码、依赖或迁移框架绕过授权。 |

修复前回答：原输入为何失败、预期行为由什么证明、修改改变哪些条件、哪些既有分支必须保留。比较局部处理与现有规则；无法决定时交付已确认事实和缺口，不强行补代码。

字段或元素中出现某段文字，不等于该状态在当前请求中成立。区分实际状态值、已触发错误与模板、说明文字、预置校验代码、历史记录或其他对象中的相同内容。新增判定须检查一个相邻反例：同格式含有相似信息，但业务条件不成立时，是否仍会被误判。源码推导与真实执行分别说明，不为反例伪造运行记录。

每个新增业务分类条件都要说明为何足以推出目标状态，而不只是解释原样本为什么命中。保持正常业务数据，只加入同形式的非状态信息，逐步推导新旧分支结果；若新条件覆盖了正常数据，应缩小处理范围或保留原错误。无法证明分类边界时记录缺口，不把尚待确认的语义称为“已修好但未运行”。已有执行反例优先于修复方的解释和自检结论。

回修建议也需独立核对，不能把审查方提出的可选条件当成业务契约。修复已给出的反例后，还要检查同一成因的相邻变化；只排除一类正常数据不等于目标状态成立。尤其不能用“没有正向成功信息”替代目标错误确已发生的依据，或把无法确定的解析错误转换成确定业务结果。材料只能证明较窄形态时，限定处理该形态，其余继续原路径；没有足够依据就停止分类修改。

识别响应中的状态时，先核对内容所在上下文及实际生效条件；同样的文字或指令处于数据、模板、条件分支和有效错误回执中，含义可能不同。使用现有可靠解析能力；材料只支持有限响应形态时，只识别完整且有依据的形态，不通过手写不完整的词法/执行模拟器去猜任意内容是否生效。若局部修复需要不断增加排除条件或复杂控制流才能自圆其说，重新核对问题归因与修复范围；无法可靠界定时停止状态转换并保留原错误。

验证目标可以是正确轨迹，也可以是符合契约的明确业务错误，由原问题的业务依据决定。正确分类错误不等于上游恢复，进程成功不等于业务正确。审查方独立核对，不照抄修复方验收条件。

异常分类核对实际客户端、异常透传链和框架现有规则；异常父类可能同时包含传输、响应解码和其他失败，不能用父类名称证明它们属于同一业务状态。页面空态必须属于当前对象的实际生效区域，文档先后顺序、全文命中或隐藏模板不足以证明区域归属；查到对象但没有事件不等于对象不存在。新增解析须沿原始结构核对字段层级、请求对象和输出值；新增代码已确定的漏字段、错映射不能当作既有问题或普通 TODO。需要决定本次正确性的事项必须解决或明确阻断，可选后续改进才写 TODO。
